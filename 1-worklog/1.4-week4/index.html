Week 4 Worklog

Week 4 Objectives:

  • Build the backend and frontend for the user profile page in Smart Docs AI: view/update personal info, avatar upload, change password — synced between Cognito and DynamoDB.
  • Add a self-healing fallback so a missing DynamoDB profile can always be rebuilt from Cognito.
  • Replace the “Sign in with Google” placeholder button with a real Cognito Hosted UI OAuth flow on the frontend.

Tasks to be carried out this week:

DayTaskStart DateCompletion DateReference Material
2- Reviewed the backend structure for the profile page and mapped out the four API routes needed: GET /api/profile, PUT /api/profile/personal-info, PUT /api/profile/avatar, POST /api/profile/change-password
 + Reviewed the token-extraction helpers each route relies on (extract_user_id_from_token, extract_cognito_username_from_token, extract_claims_from_token) — all decode the JWT payload straight from the Bearer header without a round trip to Cognito, but admin_* calls need the real Cognito Username (= email for native users, Google_xxx for linked accounts), not the sub		07/13/202607/13/2026
3- Implemented the profile retrieval flow with a self-healing fallback:
 + get_user_profile(user_id): reads the item straight from DynamoDB (smartdocai-user-profiles) by user_id (Cognito sub)
 + ensure_user_profile(user_id): if no item exists, calls Cognito list_users with Filter=sub="{user_id}" (can’t use admin_get_user(Username=user_id) since this pool uses email as Username, not sub), pulls email/name/phone_number/birthdate from the matched user’s attributes, then put_item with ConditionExpression=attribute_not_exists(user_id) so a concurrent request can’t overwrite a profile someone else just created — catches ConditionalCheckFailedException and re-reads instead
 + Wired into GET /api/profile		07/14/202607/14/2026
4- Built the personal-info update flow for fullname, email, phone, and DOB:
 + Validation: rejects empty fields, regex-checks email format, normalizes phone to E.164 via normalize_phone() (leading 0 → +84) then regex-checks the result, regex-checks dob as YYYY-MM-DD
 + Sync pattern in update_personal_info(): updates Cognito first via admin_update_user_attributes (source of truth) — if that call fails, the request aborts immediately without touching DynamoDB; only then updates DynamoDB (create_or_update_profile) as a cache — if that second step fails, it just logs a warning instead of failing the request, since Cognito already succeeded (eventual consistency)
 + Wired into PUT /api/profile/personal-info, using extract_cognito_username_from_token (not sub) to identify the user to Cognito		07/15/202607/15/2026AdminUpdateUserAttributes – Cognito
5- Added avatar upload and change-password handling:
 + update_avatar(): decodes the base64 payload (strips the data: URI prefix), rejects anything over 5MB; if the decoded image is under 300KB it’s stored as base64 directly in the DynamoDB item, otherwise it’s uploaded to S3 at avatars/{user_id}/{uuid}.jpg and only the avatar_url is kept in DynamoDB (dropping any old inline base64 field)
 + On the frontend, added a resizeImage() step before upload (canvas resize to 300px width, JPEG quality 0.7) so most avatars land under the 300KB DynamoDB path instead of hitting S3
 + change_password(): calls admin_set_user_password(Permanent=True); only requires the current password if the profile’s password_set flag is already true (so a Google-only account can set its first password without one); enforces a minimum length of 6 characters; flips password_set to true in DynamoDB on success
 + Wired into POST /api/profile/change-password, which reads password_set via ensure_user_profile() first to decide whether current_password is required		07/16/202607/16/2026AdminSetUserPassword – Cognito
6- Implemented the “Sign in with Google” frontend flow:
 + Added src/api/cognitoOAuth.js with getGoogleLoginUrl() (builds the Cognito Hosted UI authorize URL with identity_provider=Google), exchangeCodeForTokens() (exchanges the auth code for tokens at /oauth2/token), decodeJwtPayload() (client-side claim decoding for UI display only — never used for verification), and persistCognitoSession() (writes tokens to sessionStorage using the exact key format amazon-cognito-identity-js expects, so ProtectedRoute and axiosConfig keep working unmodified)
 + Added src/features/auth/pages/GoogleCallbackPage.jsx to handle the /auth/callback redirect: reads code/error from the query string, guards against a double-run under React StrictMode with useRef, dispatches the login, then routes to /app on success or back to /login with a toast on failure
 + Added the loginWithGoogleCode async thunk and its pending/fulfilled/rejected reducer cases to authSlice.js
 + Wired the Google button in LoginForm.jsx to redirect via getGoogleLoginUrl() instead of showing the old “coming soon” toast
 + Registered the new /auth/callback route in App.jsx		07/17/202607/17/2026Using social identity providers with a user pool – Cognito
7- Manually walked through the Google login flow end-to-end (button → Hosted UI → callback → token exchange → session persisted) and cleaned up a duplicate comment left in authSlice.js from the previous day’s edit
 + Synced with the backend’s same-day Google account-linking / PreSignUp trigger work so the frontend flow lines up with a user’s linked native account when emails match		07/18/202607/18/2026

  • Built the core backend API for the user profile page: retrieval with self-healing recovery, personal-info updates synced Cognito-first/DynamoDB-second, avatar upload split between DynamoDB (small images) and S3 (large images), and password changes gated by whether a password had already been set.
  • Enabled profile creation and retrieval to survive a missing DynamoDB record by rebuilding it from Cognito attributes on demand.
  • Shipped a working “Sign in with Google” flow end-to-end on the frontend, built on top of the profile-page work above.
